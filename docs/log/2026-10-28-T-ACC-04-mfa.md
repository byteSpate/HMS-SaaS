# T-ACC-04: TOTP second factor for administrators and finance staff

- **Date:** 2026-10-28
- **Commit:** this commit
- **Implements:** T-ACC-04; FR-ACC-006; UC-ACC-01 step 3; AT-ACC-009, AT-ACC-010; C-032; ADR-004; D section 7.1

## What was built

A membership whose roles come from the administrator or finance template (C-032), or that holds any `admin.*` permission, needs a second factor. After password (and hospital) such a session can still read its own session, switch language and sign out, but every permission-guarded route answers `403 MFA_REQUIRED` until the session has passed the factor. The staff app sends the user to `/staff/mfa`:

- **First time:** "Show the set-up code" gives a QR code and the key as text; the first 6-digit code turns the factor on and shows ten recovery codes once.
- **Later sign-ins:** the 6-digit code from the app, or one recovery code.

| Method and path                           | Purpose                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| `POST /api/v1/auth/mfa/enrolment`         | New secret (base32 text and `otpauth://` URI); replaces an unconfirmed one |
| `POST /api/v1/auth/mfa/enrolment/confirm` | First code turns the factor on; returns the session and 10 recovery codes  |
| `POST /api/v1/auth/mfa/verify`            | `{ "code" }` or `{ "recoveryCode" }`; returns the new session              |

Every success rotates the session ID (new cookie, new CSRF token). The session response gains `mfa: { required, enrolled, verified }`.

## Decisions applied

- **C-032:** MFA for administrator and finance roles. **ADR-004 / D 7.1:** TOTP, recovery codes stored hashed, session ID rotated at step-up.
- **T-ACC-03 lock applies:** a wrong code (or a replayed one, or a wrong recovery code) is a failed attempt; five lock the account, which also ends the session.
- **Chosen in this task:**
  - Privileged also means "holds any `admin.*` permission", so a renamed or custom role cannot avoid MFA. Per-hospital MFA role lists (CP-12) wait for policy versions (T-PLT-05).
  - The requirement is checked in `PermissionGuard` with the access data it already loads (one more indexed query in that transaction). Routes without a permission (session, language, logout, MFA itself) stay open, so the user can get through or sign out.
  - The factor belongs to the user: passing it once in a login carries over a hospital switch.
  - TOTP written in-house (about 50 lines, RFC test vectors in the spec) instead of a dependency; SHA-1, 6 digits, 30 s, one step either side, which every common app supports.
  - Replay is blocked by storing the last used time step and refusing any step at or before it.
  - The secret is encrypted, not hashed, because it must be read back; the key lives only in the environment.
  - Enrolment never replaces an enabled factor (`409 INVALID_TRANSITION`); a lost factor is reset by an administrator (T-ACC-05).
  - The web app caches the confirmed session only after the recovery codes are acknowledged, so the route guard cannot leave the screen while they are shown.
  - QR codes: `qrcode-generator` 1.4.4 (no dependencies, MIT) computes the grid; React draws it as SVG, so no markup is injected and the CSP is unchanged.

## Known limitations

- First enrolment trusts whoever holds the password (trust on first use). An attacker with an administrator's password, before that administrator has enrolled, could enrol their own phone. Go-live requires an administrator with MFA enrolled (FR-CFG-006); an admin reset of another user's factor comes with T-ACC-05.
- No "remember this device" option: the factor is asked at every login.
- Changing `MFA_ENCRYPTION_KEY` makes every enrolled factor unreadable (users must be reset). Key rotation is not built.
- The Bangla texts are proposals until a native speaker reviews them (Q-050).

## Deploy impact

- **Required new env var `MFA_ENCRYPTION_KEY`** (32 bytes, base64, `openssl rand -base64 32`). The API refuses to start without it. Optional `MFA_ISSUER`.
- Migration `20261028110000_totp_mfa`: expand-only (two new tables, one nullable column, one grant).
- New web dependency `qrcode-generator` 1.4.4. No new service or CORS change.

## How to debug

- **403 `MFA_REQUIRED`:** `GET /api/v1/auth/session` shows `mfa`; the audit trail has `authz.access.denied` with `reason = 'MFA_REQUIRED'`.
- **Code always refused:** check the phone's clock (codes allow 30 seconds of drift), and `auth_event` rows `auth.mfa.failed` with reason `BAD_CODE`, `CODE_REUSED` or `BAD_RECOVERY_CODE`.
- **User lost the phone and the recovery codes:** an administrator resets the factor (T-ACC-05); until then an operator deletes the user's rows in `hms.user_mfa` and `hms.user_mfa_recovery_code` and records it by hand.
- **API does not start:** `MFA_ENCRYPTION_KEY must be 32 bytes in base64`.
- **Locally:** add `MFA_ENCRYPTION_KEY` from `.env.example` to `.env`, `pnpm db:deploy`, then `pnpm --filter @hms/mod-identity-access exec vitest run src/application/mfa.service.spec.ts`.
