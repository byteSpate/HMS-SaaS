# ADR-019 — Supabase as managed PostgreSQL 17

- **Status:** ACCEPTED by the product owner on 2026-10-13. Plan tier and project region still open.
- **Date:** 2026-10-13
- **Amends:** [ADR-011](ADR-011-vps-topology.md) (database no longer on the VPS), D1 §4 (PostgreSQL 18 pin), J (pgBackRest backups)

## Context

- The product owner chose Supabase for the database.
- Supabase's platform default is PostgreSQL 17 (Supabase changelog, May 2026). PostgreSQL 18 support was not confirmed on 2026-10-13.
- The design relies on RLS, composite tenant keys, exclusion constraints and separate database roles. These are standard PostgreSQL and work on 17. The only PG 18 feature used was built-in `uuidv7()`.

## Decision

1. **Supabase is used only as a managed PostgreSQL server.** Supabase Auth, Storage, Realtime and the auto-generated Data API are not used. Authentication stays in NestJS (ADR-004).
2. **All tables live in the `hms` schema**, never in `public`. The project's Data API is disabled so tables cannot be reached with the anon/service keys.
3. **PostgreSQL 17** everywhere: local Docker (`postgres:17`), CI service containers and Supabase.
4. **UUIDv7 IDs are generated by Prisma** (`@default(uuid(7))`), not by the database.
5. **Connections:** migrations use the direct/session connection (port 5432) as `hms_migrator`. The app uses the transaction pooler (port 6543) as `hms_app`. Tenant context is set with `SET LOCAL` inside each transaction, which is compatible with transaction pooling.
6. **Region:** a Supabase region near the Singapore droplet (`ap-southeast-1`).
7. **Free tier for development and demos only.** Real hospital data requires a paid plan (no inactivity pausing, daily backups). The plan is decided before the pilot (RG-3).

## Open checks (before first Supabase deploy)

- Whether the Supabase `postgres` role can create `hms_migrator`/`hms_app` and grant `NOBYPASSRLS`. The `BYPASSRLS` roles in E (`hms_relay`, `hms_control`) may not be grantable on Supabase. If not, an amendment redesigns those paths.
- Whether required extensions (`btree_gist` for bed occupancy, `pg_trgm` for patient search) are available. Both are in Supabase's extension list but must be enabled and tested.
- Backup and restore drill (RB-07) against Supabase's backup feature, replacing pgBackRest.

## Results on 2026-10-13 (project in ap-southeast-1)

- Server is PostgreSQL **17.11**, the same as local Docker.
- The Supabase `postgres` role has CREATEROLE and BYPASSRLS (not superuser). `hms_migrator` and `hms_app` were created with `NOBYPASSRLS` using `docker/postgres/supabase/10-roles.sql`. Creating the `BYPASSRLS` roles (`hms_relay`, `hms_control`) is still untested.
- `btree_gist` 1.7 and `pg_trgm` 1.6 are available (not yet enabled).
- `prisma migrate deploy` as `hms_migrator` through the session pooler applied the first migration. `hms_app` reads `hms.tenant` through the transaction pooler. `anon` and `authenticated` have no usage on schema `hms`.
- Still to do in the dashboard: disable the Data API (Project Settings → Data API). Backup/restore drill not done.

## Consequences

- Positive: no database server to patch, back up or monitor on the droplet. The droplet keeps RAM for the apps.
- Negative: less control over superuser features. Cost grows with database size. Patient data sits with a third-party processor (DEF-001 still defers the legal review).
